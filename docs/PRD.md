# 집안일 알림 서비스 PRD

> 본 문서는 초기 기획 초안을 바탕으로 재구성한 정식 PRD입니다. 계속 업데이트될 예정이며, 각 섹션은 독립적으로 수정 가능하도록 헤딩을 분리했습니다. 미확정 항목은 `[확인 필요]`로 표시하며, 임의로 답을 채우지 않았습니다.

## 개요

### 한 줄 정의

1인 가구를 위한, 주기를 가지는 모든 집안일(청소·화분 물주기 등)의 일정을 관리하고 알림을 보내주는 앱

### 배경

- 본인이 직접 자취하면서 집안일을 깜빡하거나 주기를 놓친 불편 경험이 출발점
- 이를 해결하기 위해 개인용으로 텔레그램 봇 기반 알림 도구를 만들어 사용 중이었음
- 다른 1인 가구도 비슷한 불편을 겪을 것으로 판단해, 앱인토스 공개 서비스로 확장하기로 함

## 타겟 사용자

- 1인 가구 (확정)
- 그중에서도 **자취/독립 생활 경력이 짧은 사람** (예: 자취를 시작한 지 얼마 안 된 사회초년생) 쪽으로 좁혀서 설계 (확정)
  - 집안일을 "무엇을 어느 주기로 해야 하는지" 자체를 아직 잘 모르는 사람이 많다는 전제 → 기본 제공 집안일 템플릿/추천 주기 제공이 핵심 가치가 됨

`[확인 필요]`
- "경력이 짧다"를 구체적으로 어떻게 정의할지 (예: 자취 시작 후 1년 이내 같은 기간 기준, 혹은 사회초년생/대학생 같은 생활 단계 기준). 지금은 느슨하게만 정의해두고, 이후 사용자 조사 등을 통해 구체화 예정

## 핵심 기능 명세

총 3개 화면(메인 / 집안일 리스트 / 캘린더)과 알림 로직으로 구성됩니다.

**목적:** 집안일 항목을 등록·관리하는 화면

**주요 기능:**
- 신규 등록: 별도 페이지(`/chores/new`)에서 이름, 유형, 반복 방식, 최초 시작일 입력
- 수정: 별도 페이지(`/chores/:id/edit`)에서 기존 값 불러와 수정
- 활성/비활성 전환: 리스트에서 각 항목 왼쪽 체크 토글 (삭제 대신 비활성화 옵션 제공)
- 삭제: 리스트에서 각 항목의 "삭제" 버튼(수정 버튼 옆, 빨간색)

**집안일 유형 (2가지)**

| 유형 | 설명 | 주기 계산 방식 | 예시 |
|---|---|---|---|
| 일반 반복형 | 입력한 주기에 따라 계속 반복. 반복 방식으로 "날짜 고정"과 "주기" 중 선택 | 아래 "일반 반복형의 반복 방식" 참고 | 화장실 청소 (3주 주기), 칫솔 바꾸기 (매달 1일), 에어컨 청소 (매년 5월 20일, 날짜 고정) |
| 수시 등록형 | 주기 없이 일회성 | 주기 없음: 등록한 날짜 1회만 실행 | 창고 정리 |

**일반 반복형의 반복 방식 (2가지 중 선택)**

일반 반복형을 선택하면 아래 두 반복 방식 중 하나를 고르고, 그에 맞는 세부 주기를 입력함:

| 반복 방식 | 설명 | 계산 방식 | 예시 |
|---|---|---|---|
| 날짜 고정 | 매달 또는 매년 같은 날짜에 반복 | 절대 주기: 완료 여부와 무관하게 지정한 날짜(매달 N일, 또는 매년 M월 N일)에 자동 재등장 | 칫솔 바꾸기 (매달 1일), 에어컨 청소 (매년 5월 20일) |
| 주기 | N일/N주 등 간격으로 반복 | 상대 주기: 완료일(또는 마지막 실행일) 기준 +N일/N주 뒤로 계속 밀려감 | 화장실 청소 (3주마다) |

**날짜 고정 방식(매년) 수정 시 적용 시점**

수정 시점에 새 날짜가 올해 기준으로 아직 지나지 않았는지에 따라 다름:
- 수정 시점에 **새 날짜가 아직 안 지났다면** → 올해도 새 날짜로 즉시 반영 (예: 1월에 5/20 → 6/1로 수정 → 올해도 6/1에 알림)
- 수정 시점에 **새 날짜가 이미 지났다면** → 올해는 원래 예정대로 두고(미완료 상태면 그대로 유지), 내년부터 새 날짜 적용 (예: 8월에 6/1로 수정 → 올해는 그대로, 내년 6/1부터 적용)

### 캘린더 페이지

> **2026-08-16~17 UI 개편**: 실기기 QR 테스트 피드백을 반영해 캘린더 화면을 아래와 같이 재구현 (`src/pages/CalendarPage.tsx`).
> - 날짜 칸: 항목 이름을 나열하던 방식에서 원형(각진 사각원) 배지 안에 날짜 숫자 + 상태 점 하나로 요약하는 방식으로 변경. 오늘은 테두리만(fill 없음), 탭으로 선택한 날짜는 연한 파란 배경(fill, 테두리 없음)으로 표시하며 둘 다 해당하면 동시 표시
>   - 점 색 규칙: 그 날짜의 모든 항목이 완료면 파랑, 미완료가 하나라도 있고 오늘 이전(지난 날)이면 빨강, 미완료가 있고 오늘/미래면 회색, 항목이 없으면 점 없음
> - 캘린더 진입 시 오늘 날짜가 기본으로 선택된 상태로 시작 (달을 이동하면 선택 해제)
> - 월 이동: 상단에 "YYYY년 M월"을 볼드로 표시하고 그 오른쪽에 `<`/`>` 화살표 아이콘으로 이동. 연/월을 직접 골라 점프하는 방식은 검토했으나 제외하고 화살표 이동만 유지
> - 상세 영역(선택한 날짜의 항목 목록) 카드의 왼쪽 색바를 상태별로 세분화: 완료(파랑) / 예정(회색) / 지난 날인데 미완료(빨강)
> - "이날 한 집안일 추가" 버튼을 누르면 바로 `BottomSheet`가 열려 그 안에서 집안일 하나를 선택하고, 하단 좌우 버튼(취소/추가하기)으로 확정하는 구조로 구현(중간 선택 박스 단계 없음)
>
> **2026-08-19 기획 확정 (미구현)**: 실사용 중 발견한 세 가지 개선사항을 기획으로 확정. 아직 코드 구현 전이며, 상세 내용은 아래 "수기 입력 기능", "재알림 일수를 다 채우고도 미완료인 경우" 항목에 반영.
> 1. 수기 입력 삭제 기능
> 2. 미완료 항목을 늦게 완료 처리할 때 "실제로 한 날짜"를 직접 지정하는 기능("다른 날 완료")
> 3. 완료 항목의 pill(정기 수행/수기 입력) 옆에 다음 예정일 표시

**목적:** 등록된 집안일을 캘린더 뷰로 확인

**주요 기능:**
- **월간 뷰만 지원** (주간 뷰는 제공하지 않음 — 하루 항목 수가 많지 않은 서비스 특성상 월간 뷰만으로 충분)
- 앞으로 해야 하는 집안일 (예정)
- 이미 완료한 집안일 내역 (히스토리)
- 날짜 칸에 표시되는 기준:
  - **완료된 항목**: 실제로 완료 처리한 날짜의 칸에 표시 (예정일이 아니라 완료일 기준). 예: 1/1 최초알림인데 1/3에 완료 처리 → 1/3 칸에 표시
  - **미완료 항목**: 원래 예정일(최초알림일) 칸에 그대로 표시. 다음 주기가 도래해도 이전 미완료 건은 삭제/병합되지 않고 각자 독립된 기록으로 남음 (한 달에 여러 번 미완료가 쌓이는 것도 의도된 동작 — 사용자가 얼마나 밀렸는지 확인할 수 있어야 함)
- 완료된 항목이 다음 주기 기준점이 되는 규칙([알림 로직](#알림-로직) 참고)과 별개로, **완료를 아예 하지 않은 경우 다음 예정일은 원래 주기 계산대로 그대로 도래**하며 그 시점에 새 최초알림이 시작됨. 기존 미완료 건은 그대로 남고 새 항목과는 무관하게 별개로 취급됨
- 캘린더에서 날짜 칸을 탭하면 그 날짜의 모든 항목이 함께 펼쳐지고, 각 항목의 상세 정보로 **완료/미완료 여부**와 **정기 수행 / 수기 입력 여부**를 보여줌 (완료 시각 등 그 외 정보는 표시하지 않음)
- **완료 처리는 캘린더에서도 가능** (2026-08-15 변경 — 최초 정의는 보기 전용이었으나 실사용 확인 후 캘린더에서도 체크 가능하도록 확정). 완료 처리하면 표시 기준이 예정일 → 완료일로 바뀌므로, 오늘이 아닌 날짜에서 완료 처리한 항목은 캘린더상 그날(완료 처리한 날) 칸으로 이동해서 보임
- **다음 예정일 표시** (2026-08-19 기획 확정, 미구현): 완료된 항목의 "정기 수행"/"수기 입력" pill 옆에 다음 예정일을 함께 표시
  - 표시 대상은 그 집안일의 **가장 최근 완료건에만** — 예: 8/1 정기수행 완료 후 8/15에 수기입력으로 또 완료(중복 허용, 더 최근)했다면 8/15 건에만 다음 예정일 표시, 8/1 건에는 표시 안 함(그 시점 기준 다음 예정이 이미 8/1이 아니게 되었으므로 혼동 방지)
  - 표시값은 새로 계산하지 않고, 이미 생성돼 있는 다음 occurrence(미완료)의 예정일을 그대로 조회해 표시 — 조회 시점마다 다음 occurrence를 미리 생성해두는 기존 로직(`ensureOccurrencesUpTo`)에 의존
  - 수시 등록형(1회성)은 다음 회차가 없으므로 아무것도 표시하지 않음

**사용자 알림 설정 (3가지, 모두 커스터마이징 가능)**

| 설정 항목 | 설명 | 디폴트 |
|---|---|---|
| 알림 시간 | 해야 하는 집안일 앱 푸시가 나가는 시각 (매일 필수 발송) | 08:00 |
| 리마인드 재알림 시간 | 원하는 사용자만 켜서 쓰는 하루 두 번째 알림 시각 (토글로 on/off) | 21:00 (토글 off가 기본) |
| 재알림 일수 | 최초알림일 이후 며칠 더 재알림을 보낼지. 예: 2일로 설정하면 최초알림일 + 1차 재알림일 + 2차 재알림일, 총 3일간 알림 발송. 설정 변경 시 이미 진행 중인 모든 미완료 항목에도 즉시 적용됨(소급 적용) | 2일 |

**발송 구조**

미완료 항목은 예정일(최초알림일)부터 "재알림 일수"만큼 매일 계속 알림 대상이 되며, 하루 중 알림 시간(및 켜져 있다면 리마인드 재알림 시간)에 발송됨. 항목마다 자기 예정일을 기준으로 독립적으로 카운트됨.

예: 1/1 세탁조 청소, 1/3 바닥청소가 예정이고 재알림 일수 2일, 알림 시간 08:00, 리마인드 21:00(활성)인 경우
- 1/1: 세탁조 청소 최초알림 (08:00, 21:00)
- 1/2: 세탁조 청소 1차 재알림 (08:00, 21:00)
- 1/3: 세탁조 청소 2차 재알림 + 바닥청소 최초알림 (08:00, 21:00)
- 1/4: 세탁조 청소는 재알림 일수(2일) 소진 → 더 이상 알림 없음. 단, 항목 자체는 계속 미완료 상태로 남고, 사용자가 메인/캘린더에서 언제든 완료 체크 가능

**알림 묶음 처리**

- 같은 시각에 알림 대상 항목이 여러 개면, **알림 유형(최초알림/재알림)이 같은 것끼리만** 하나의 푸시로 묶어서 발송. 최초알림과 재알림이 같은 시각에 섞이면 묶지 않고 **별개의 푸시로 분리 발송**
  - 예: 1/3 08:00 → 푸시 A "[재알림] 세탁조 청소", 푸시 B "[오늘 할 일] 바닥청소" (2건 발송)
  - 예: 최초알림 대상이 2개 이상이면 그것들끼리는 하나로 묶임 ("오늘 할 일 2건: 화장실 청소 외 1건"), 재알림도 마찬가지
- 알림을 탭하면 앱(메인 페이지)으로 진입하고, 완료 처리는 메인 페이지에서만 가능. 알림 자체에서 완료 액션 버튼으로 처리하는 기능은 제공하지 않음 (묶인 알림은 액션 버튼으로 "어떤 항목을 완료할지" 특정할 수 없어 개별 처리와 양립 불가)
- 리마인드 재알림(21:00) 토글은 그 시각 발송 여부만 결정하며, 알림 시간(08:00)의 최초알림/재알림 발송이나 재알림 일수 카운트에는 영향을 주지 않음
- 당일 먼저 온 알림(예: 08:00 최초알림)을 받은 뒤 완료 체크하면, 그날 이후 알림(예: 21:00 리마인드)의 묶음 대상에서 해당 항목은 자동 제외됨

- **수기 입력 기능** (2026-08-15 개념 정리): 등록된 집안일을 예정에 없이(불시에) 완료했을 때 수동으로 완료 기록을 남기는 기능
  - **정기 수행 vs 수기 입력**: 정기 수행은 집안일 리스트에 등록된 일정(예정일)대로 완료 처리한 것. 수기 입력은 예정과 무관하게 그 집안일을 했다고 새로 기록하는 것. 두 값은 각 occurrence의 `completion_type`으로 구분됨(`regular` / `manual`)
  - **진입 경로**: 캘린더 페이지에서 날짜 칸을 선택 → "이날 한 집안일 추가" 버튼 → 완료 날짜는 선택한 그 날짜로 고정됨
  - **선택 대상**: 활성화된 집안일 전체 (그날 예정 여부와 무관)
  - **기존 미완료 예정과의 관계**: 그 집안일에 이미 방치된 미완료(pending) 건이 있어도 그대로 둠 — 수기 입력은 별개의 새 기록이며 기존 미완료 건을 대신 완료 처리하지 않음
  - **중복 완료 허용**: 같은 주기 내에 이미 정기 수행으로 완료된 집안일도 수기 입력으로 추가 기록 가능
  - **다음 주기 재계산**: 수기 입력한 날짜가 다음 주기의 새 기준점이 됨(일반 반복형에 한함). 이미 생성돼 있던, 그 수기입력 날짜 이후의 미완료 예정은 삭제되고 새 기준일로 다시 계산됨
  - 예시: 이불솜 파손으로 세탁조 청소를 예정에 없이 했을 때
  - **삭제 기능** (2026-08-19 기획 확정, 미구현): 캘린더 상세에서 수기 입력 항목 오른쪽에 X 버튼 표시, 누르면 확인 단계("정말 삭제할까요?")를 거쳐 삭제. 정기 수행 항목에는 이 삭제 버튼이 없음(정기 수행은 체크 재탭으로 완료 취소만 가능, 삭제 대상 아님)
    - 체크 해제(미완료로 되돌리기)가 아니라 occurrence 자체를 **완전히 삭제** — 예정에도 없던 기록이 미완료 상태로 남는 건 의미가 없으므로
    - 삭제 시, 그 수기 입력을 기준으로 이미 생성돼 있던 다음 예정(미완료) occurrence도 함께 삭제하고, 남은 항목 중 가장 최근 완료건을 기준으로 다음 예정을 다시 생성 — 수기 입력이 애초에 없었던 것처럼 완전히 복원 (기존 `ensureOccurrencesUpTo` 로직 재사용)
- 알림 방식: 로컬 버전은 텔레그램 봇이었으나, 앱인토스 공개 서비스로 갈 경우 토스 인앱 푸시 알림으로 전환 (별도 논의 완료 — 아키텍처 문서 참고)

**재알림 일수를 다 채우고도 미완료인 경우**

- 알림은 멈추지만, 항목은 자동 스킵되지 않고 **계속 미완료 상태로 남김**
- 이후 사용자가 늦게라도 완료 체크하면, 실제 완료 처리한 날짜가 다음 주기의 새 기준점이 됨
  - 예: 원래 예정일 1/1, 재알림 소진 후에도 방치하다가 1/10에 완료 체크 → 1/10이 다음 주기 계산의 기준일이 됨 (수기 입력과 동일한 규칙)
  - 단, 이 규칙은 **일반 반복형 중 "주기" 방식에만 적용**됨. "날짜 고정" 방식(매달/매년)은 완료 시점과 무관하게 정의된 날짜가 항상 고정이므로, 늦게 완료해도 다음 회차 일정은 이동하지 않음 (예: 매년 5/20 항목을 5/28에 완료해도 내년 일정은 그대로 5/20)

**"다른 날 완료" 기능** (2026-08-19 기획 확정, 미구현)

미완료 항목을 늦게 완료 처리할 때, "체크하는 시점"과 "실제로 그 집안일을 한 날"이 다를 수 있음(예: 8/1 예정을 안 해서 8/2에 알림이 왔고, 8/2에 실제로 수행해서 체크). 지금 규칙대로면 completed_date가 체크한 시점(오늘)으로 고정되는데, 사용자가 원하면 실제로 한 날짜를 직접 지정할 수 있게 함.

- **위치**: 캘린더 상세에서 미완료 항목을 볼 때, 기존 체크박스 옆에 "다른 날 완료" 버튼을 추가로 표시
- **동작**: 버튼을 누르면 월력(캘린더 그리드) 형태의 날짜 피커가 열림 — 이전 달로 계속 넘기며 과거를 자유롭게 탐색 가능. 선택 가능 범위는 **과거 무제한 ~ 오늘까지** (미래 선택 불가, 예정일 이전 날짜도 선택 가능 — 예정일보다 미리 했을 수도 있으므로 하한을 예정일로 제한하지 않음)
- **결과**: 선택한 날짜가 그대로 completed_date로 저장됨. 화면상 위치는 "이동"이 아니라, 기존 규칙 그대로 완료 처리 시 표시 기준이 scheduled_date → completed_date(사용자가 지정한 날짜)로 바뀌는 것
- **다음 주기 계산**: 사용자가 지정한 날짜를 그대로 기준점으로 사용 — 기존 "완료일이 다음 주기 기준"이라는 규칙과 완전히 동일하게 적용, 새 필드나 별도 로직 불필요
- 새 개념이 아니라, 기존 정기 수행의 completed_date를 "오늘로 자동 고정" 대신 "사용자가 지정 가능"하도록 확장하는 것. `completion_type`은 여전히 `regular`
- **적용 범위**: 캘린더에서만 제공. 메인 페이지(오늘 할 일 박스)의 체크박스는 "탭 1회 = 오늘 날짜로 즉시 완료"라는 단순함을 유지하기 위해 변경하지 않음

> 알림 로직 관련 확인 필요 항목은 모두 해소됨.

### 회원가입 / 로그인

> **2026-08-11 변경**: 토스 로그인은 사업자등록이 필수라는 것을 확인. 사업자등록 없이 개발/출시를 진행하기 위해 **토스 로그인 대신 앱인토스 SDK의 익명 식별키(`getAnonymousKey`) 방식으로 전환**. 아래는 변경된 최종 방식.

- 별도 로그인 화면/회원가입 폼 없음. 앱 진입 시 SDK의 `getAnonymousKey()`를 호출해 사용자별 고유 익명 키(hash)를 받아옴
- 같은 사용자는 앱을 껐다 켜도 항상 동일한 키를 받으므로, 이 키를 기준으로 각자의 집안일 데이터가 계속 유지됨 (일반적인 사용 흐름에서는 데이터 유지 문제 없음)
- 서버(백엔드)는 이 키를 앱인토스 서버 API로 검증한 뒤, 내부 `user_id`와 매핑해 데이터를 저장/조회함 (서버 통신에는 mTLS 인증서 필요)
- 클라이언트는 Supabase에 직접 접근하지 않고, 항상 서버(Edge Function)를 거쳐서 데이터에 접근함. 서버가 익명 키를 검증하고 그 사용자의 데이터만 접근하도록 하며, Supabase RLS는 서버(service_role)만 전체 접근 가능하도록 잠가둠
- 토스 로그인 특유의 "연결 해제 콜백/30일 유예 삭제" 개념은 익명키 방식에는 해당하지 않아 적용하지 않음 (사업자등록 후 토스 로그인으로 전환하게 되면 재검토 필요)

> **2026-08-12 구현 완료**: 위 방식대로 실제 구현 및 배포까지 완료. 프론트엔드(`src/hooks/useAnonymousKey.ts`의 `useCurrentUser()`)가 `User.getAnonymousKey()` 호출 후 서버로 검증을 요청하고, 서버(Supabase Edge Function `verify-user`)가 mTLS로 앱인토스 검증 API를 호출한 뒤 `users` 테이블에 upsert하는 흐름까지 배포 완료. mTLS 인증서 발급도 완료(콘솔 "mTLS 인증서" 메뉴). 다만 로컬 브라우저는 SDK 네이티브 브릿지가 없어 실제 익명키를 받을 수 없으므로, 전체 흐름의 최종 검증은 실기기 QR 테스트로 남아 있음.

## 데이터 모델 초안

지금까지 확정된 화면/알림 로직을 기준으로 정리한 초안. 실제 구현 시 세부 타입/제약조건은 조정될 수 있음.

### User (사용자)

| 필드 | 설명 |
|---|---|
| id | 사용자 식별자 (Supabase UUID, PK) |
| anon_key | 앱인토스 SDK `getAnonymousKey()`로 받은 익명 식별키 (고유값) |
| notification_time | 알림 시간 (기본 08:00) |
| reminder_time | 리마인드 재알림 시간 (기본 21:00) |
| reminder_time_enabled | 리마인드 재알림 사용 여부 (기본 false) |
| reminder_days | 재알림 일수 (기본 2일) |

### Chore (집안일 항목)

| 필드 | 설명 |
|---|---|
| id | 집안일 식별자 |
| user_id | 소유 사용자 |
| name | 집안일 이름 |
| type | 유형 — `general`(일반 반복형) / `one_time`(수시 등록형) |
| repeat_mode | 일반 반복형일 때만 사용 — `fixed_date`(날짜 고정) / `interval`(주기) |
| interval_value | `repeat_mode = interval`일 때 주기 값 (예: 3) |
| interval_unit | `repeat_mode = interval`일 때 주기 단위 — `day` / `week` |
| fixed_unit | `repeat_mode = fixed_date`일 때 — `month`(매달) / `year`(매년) |
| fixed_month | 고정 날짜의 월 (매년 반복일 때만 사용) |
| fixed_day | 고정 날짜의 일 |
| start_date | 최초 시작일 (신규 등록 시 입력) |
| is_active | 활성/비활성 여부 (삭제 대신 비활성화) |
| created_at / updated_at | 생성/수정 시각 |

### ChoreOccurrence (집안일 회차별 실행 기록)

집안일 하나가 주기마다 생성하는 개별 실행 건. 완료/미완료, 캘린더 표시, 재알림 카운트가 모두 이 단위로 관리됨.

| 필드 | 설명 |
|---|---|
| id | 실행 건 식별자 |
| chore_id | 소속 집안일 |
| scheduled_date | 예정일(최초알림일) |
| status | `pending`(미완료) / `done`(완료) |
| completed_date | 완료 처리한 날짜 (완료 시에만 값 존재, 캘린더 표시 기준) |
| completion_type | `regular`(정기 수행) / `manual`(수기 입력) |
| reminder_count | 현재까지 발송된 재알림 차수 (재알림 일수 소진 여부 판단용) |

### `[확인 필요]`
- 위 필드는 초안이며, 실제 구현 단계에서 세부 타입/인덱스/제약조건은 조정 필요
- 알림 발송 이력을 별도 로그 테이블로 관리할지 여부 (재발송 방지, 디버깅용)

> 참고: 앱인토스는 자체 DB를 제공하지 않음. 앱인토스 SDK의 `Storage`는 기기 로컬 저장소로, 앱 삭제 시 데이터가 함께 삭제되어 이 서비스처럼 서버가 알림을 스케줄링하고 기록을 영구 보존해야 하는 경우엔 부적합. 위 데이터 모델은 별도의 외부 백엔드(예: Supabase 등 PostgreSQL 기반 서비스, 공식 문서에서 연동 가이드 제공)에 구축하는 것을 전제로 함.
>
> **백엔드로 Supabase(PostgreSQL) 확정 (2026-08-11)**. `users` / `chores` / `chore_occurrences` 3개 테이블을 실제로 생성 완료. RLS는 `service_role`만 전체 접근 가능하도록 설정 — 클라이언트(프론트엔드)는 Supabase에 직접 접근하지 않고 항상 서버(Edge Function)를 거쳐 데이터에 접근하는 구조.
